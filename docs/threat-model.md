# Threat model

Version 0.2 · 2026-10-29 · Method: STRIDE per trust boundary. Reviewed at the end of every phase.

## Assets

1. Vault notes (personal health, job search and journal data): confidentiality and integrity.
2. Google OAuth refresh token (phase 2).
3. Integrity of the released installer and its dependencies.
4. Health data from Apple Health exports (phase 3): confidentiality.
5. Money records: transactions, budgets, balances with friends (phase 4): confidentiality and integrity.

## Trust boundaries

```
[Vault files] --(B1)--> [Rust core] <--(B2: IPC)--> [WebView UI]
                            |  \
                         (B3)   (B4: HTTPS)
                     [index.db]   [Google Sheets API]
[Health export folder (iCloud Drive)] --(B6)--> [Rust core]
[Bank CSV files] --(B7)--> [Rust core] --> [Vault Money/]
[Source + deps] --(B5: CI/CD)--> [Signed installer] --> [Owner's PC]
```

## Note on B6 (health export folder)

Sample data mode (T23) never reads this folder: `get_health` takes its folder from the mode, not from the owner's settings, and the picker and Remove commands are refused while sample data is on.

The health folder is chosen with a native picker and stored in local settings, like the vault, and the UI never sends a path. It differs from the vault in one rule: iCloud for Windows marks every synced file and folder as a Cloud Files reparse point, so the vault rule (refuse every reparse point) would reject the folder outright. The health guard instead refuses name-surrogate reparse points, the ones that can redirect a path elsewhere (symlinks, junctions and mount points; Rust's `FileType::is_symlink` covers all three on Windows), and allows other reparse tags. The folder, every folder walked and every file read is checked this way, and each read also canonicalises the path and requires it to stay under the canonical folder.

Limits (T16): files over 32 MB are recorded as bad and not opened; at most 2,000 `.json` files up to 3 folders deep are read, newest first, and the rest are only counted; values outside sane ranges (for example steps above 200,000 in one point, weight outside 20 to 400 kg) and values in unknown units are dropped. The item caps are applied while the JSON is read, by visitors that keep at most the cap per list and skip the remainder without building it, so a 32 MB file of empty or oddly shaped points costs neither much memory nor time: at most 200,000 points per kind per file (all entries of that kind together), 10,000 workouts per file, 64 entries in `metrics`, and the `data` of an unknown metric is held unparsed and dropped. Points without a real calendar date are not kept. Over all files at most 2,000,000 points and 10,000 workouts are merged, newest file first; once the point cap is reached the older files are not opened. A bad file is listed by file name and a fixed reason, never its content. The newest-export time used for the staleness warning comes only from files that parsed, and is never later than now.

Caching and re-reads: each parsed file is cached by relative name, size and modification time, so a refresh reads and parses only new or changed files and merges the rest from memory. This also means an iCloud placeholder is downloaded once, when it is first read, rather than on every refresh. Duplicate points are tracked as keyed 64-bit hashes. The import runs without the state lock held; clearing or changing the folder bumps a generation counter, so an import still running cannot store its result afterwards.

The folder is validated again on every load (not a link, junction or mount point, a real folder), so a chosen root later replaced by a junction is refused. Residual risk: a swap between that check and the files being opened (a time-of-check to time-of-use race) is not closed; each file is still re-checked component by component and by canonical path before it is opened, which narrows the window but does not remove it, and the attacker would already need write access to the owner's folders. Files are only opened for reading: the importer has no write, rename or delete path. Opening a placeholder that is not yet downloaded makes iCloud fetch it, so the import runs off the UI thread.

Vault writes (phase 4, T1/T2): the app writes only `Money/Ledger/YYYY-MM.md` (path built in the Rust core from a validated date) and `Money/Splits.md` (a fixed path); a category change rewrites an existing `Money/Ledger/YYYY-MM.md` only (never creates one), finding the row by its content and refusing if the note no longer has exactly the identical rows the page showed; no path is ever sent by the UI; folders are created one at a time without following links, and the note's folder and the vault root are re-checked (no link or junction, canonical path inside the vault) right before the rename. Residual risk: the same time-of-check to time-of-use window as reads, narrowed to the instant between that re-check and the rename, and again only open to someone who can already write to the owner's folders.

## Out of scope

Malware already running as the user (it can read the vault directly); physical access to an unlocked PC.
